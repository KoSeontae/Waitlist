# 부하 테스트

같은 조건에서 동시성 제어와 성능 개선의 전후를 비교하기 위한 k6 스크립트다. 앱, DB, k6가 한 머신에서 CPU를 나눠 쓰므로 절대 수치가 아니라 상대 비교에 사용한다.

## 준비

- JDK 21, Docker, k6 (`brew install k6`)
- 측정할 때는 IDE, 브라우저, 다른 컨테이너를 종료하고 전원을 연결한다

## 실행

```bash
loadtest/run.sh reserve spread 10
```

```bash
loadtest/explore.sh reserve hot
```

기준선 측정(13개 조건을 3번 반복, 약 70분)은 다음 스크립트로 실행한다. 반복 횟수는 `REPEAT`로 바꾼다.

```bash
loadtest/baseline.sh
```

측정 결과:

- [기준선 (2026-11-27)](results/2026-11-27-baseline.md)
- [예약 신청 탐색 (2026-11-27)](results/2026-11-27-reserve-exploration.md)

`run.sh`는 1회 실행마다 jar 빌드, 앱 기동(18080 포트, 힙 1GB), 시드, 워밍업, 측정, 불변식 확인, 앱 종료를 수행한다. 결과는 `build/loadtest/results.md`에 한 줄씩 쌓이고, 앱 로그는 `build/loadtest/app.log`에 남는다(실행마다 덮어씀).

| 인자 | 값 |
|---|---|
| 시나리오 | `reserve` 예약 신청 / `cancel` 대기자가 있는 회차의 예약 취소 |
| 분포 | `hot` 회차 1개에 집중 / `spread` 회차 100개에 분산 |
| 동시 사용자 | k6 VU 수 |
| 프로필 | `perf` 모든 요청이 성공하는 정원(기본값) / `limit` 정원이 작아 초과 여부를 확인(reserve만) |

| 환경 변수 | 기본값 | 설명 |
|---|---|---|
| `ITERATIONS` | reserve perf 5000, limit 3000, cancel 1000 | 측정 요청 수 |
| `POOL` | 10 | DB 커넥션 풀 크기 |
| `BUILD` | 1 | `0`이면 jar 빌드 생략 |

## 조건

- 데이터는 `waitlist_load` DB에만 만든다. 실행마다 비우고 다시 채운다
- 사용자 15,000명(측정 10,000 / 워밍업 5,000), 배경 회차 2,000개(예약 20,000건, 대기 10,000건)
- 측정은 고정된 요청 수를 보낸다. 사용자당 회차 1건 제약이 있고 데이터가 늘면 조회 비용이 달라지므로, 실행마다 같은 일을 하게 한다
- 인증 토큰은 k6가 직접 서명한다. 로그인(BCrypt) 비용이 측정에 섞이지 않게 한다
- `409`는 정상 거절로 세고, 오류에는 그 밖의 응답과 타임아웃만 포함한다

## 결과 열

| 열 | 의미 |
|---|---|
| 정원 초과 | (확정 + 기회) - 정원. 0이어야 한다 |
| 미발급 빈자리 | 대기자가 있는데 기회가 발급되지 않은 빈자리. 0이어야 한다 |
| 알림 누락 | 기회를 받았는데 알림이 없는 대기. 0이어야 한다 |
| 중복 | 같은 사용자가 같은 회차에 활성 상태를 둘 이상 가진 수. 0이어야 한다 |
| 풀 타임아웃 로그 | 커넥션을 얻지 못했다는 로그 줄 수 |
| CPU 코어 | 측정 중 평균 사용 코어 수 (앱 / DB 컨테이너 / k6) |
